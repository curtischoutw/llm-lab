結論：為什麼兩個模型會有這樣的差異

依據：兩次 eval 的答案、兩組判讀理由、2026-11-04 金融卡 ticket 05 的 context 檢查（docs/debit-card-eval.html），以及兩個模型存在快取裡的查詢關鍵字。兩次 eval 用同一份知識庫（Qwen3-4B 建的圖譜；2026-11-04 之後沒有變動，使用者確認）、同一個 embedding 與 reranker、同樣的 token 上限；不同的只有「抽查詢關鍵字」和「讀 context 寫答案」這兩步。Gemma 的 eval 沒有存下 context，所以下面凡是講 Gemma 看到什麼 context 的，都是推論。

1. Qwen 的錯有不少是「讀錯 context」，Gemma 在這些題答對

Gemma 4 多答對的 6 題（switch-02、benefit-03、rule-03、fee-01、terms-01、offer-03），Qwen 錯的地方多半是把數字、日期或主詞寫錯。其中 rule-03、switch-02 有 2026-11-04 的 context 紀錄，證實正確段落當時就在 Qwen 的 context 裡；其他 4 題沒有 context 紀錄，「是讀錯不是缺資料」是推論：

  • rule-03：Qwen 把點數清除日寫成 2028/12/31。2026-11-04 的 context 檢查顯示，寫著 2030/1/31 的段落當時就在 context 的第 1 段。Gemma 答對。
  • switch-02：Chill刷 2026/7/8 起的開放期間在 Qwen 的 context 第 5 段，Qwen 沒寫；Gemma 也沒寫，但判讀者認為這不是主要問點，其餘限制都答到，判 ✓。
  • terms-01：Qwen 把「掛失後被冒用由銀行負擔」寫反成由持卡人負擔；Gemma 答對，連例外情形也列出來。
  • offer-03：Qwen 把保險新戶期間、活動總量寫錯（350,000 份，參考答案 200,000 份）；Gemma 的日期與份數都對。
  • benefit-03：Qwen 把「每次達標享 2 次」當成全年上限；Gemma 分清楚 2 次與全年 12 次。

Gemma 4 26B A4B 是混合專家模型，總參數約 26B，每個 token 約 4B 參與運算（模型名稱的 A4B 即此意）；Qwen3-4B 是 4B。產生答案時的 prompt 約 10.7k～11.2k token（ticket 02 的 server 紀錄）。在這麼長的 context 裡對照數字、日期與條件，較大的模型表現較好，這是依答案觀察到的現象。沒有做控制實驗（例如把兩個模型的 context 固定成同一份），所以分不出多少來自寫答案、多少來自第 4 點的關鍵字差異。

2. Gemma 4 比較常說「資料不足」，比較少編答案

cross-01、cross-02、debit-wrongcard-02、debit-confuse-01 這幾題，Qwen 會寫出錯的數字或接受錯的前提；Gemma 多半改寫「文件未提供」「依公告之收費標準」或建議洽客服。分數上只有 debit-confuse-01 從 ✗ 變 △（說了兩種卡不一樣，但沒給金融卡的 100 元），cross-01、debit-wrongcard-01 仍是 ✗。原因不只一種：

  • 檢索漏掉：2026-11-04 的檢查顯示 cross-02 需要的雙幣卡頁、昇恆昌頁兩次都沒進 context。模型再大，也答不出 context 裡沒有的資料。cross-01 沒有 context 紀錄，Gemma 說 Richart 卡與街口聯名卡「文件未提供」，推測也是檢索漏掉。
  • 資料在 context 裡卻沒用上：debit-confuse-01 的金融卡 100 元段落在 Qwen 的 context 第 5 段，debit-wrongcard-02 寫明「切換刷」的段落曾在 context 第 3 段，Qwen 仍答錯。Gemma 這兩題有沒有拿到同樣的段落不知道。

3. 信用卡、金融卡分不清的問題沒有改善

金融卡 8 題的內容 ✓ 兩個模型都是 4 題；debit-wrongcard-01 兩個模型都接受「Richart 卡一般消費 0.5%」的錯誤前提，debit-negate-01 Gemma 反而從 △ 變 ✗（把信用卡的機場接送權益列在「財富管理相關卡別」底下）。2026-11-04 找到的原因仍然存在，而且都在知識庫這一側：

  • 段落沒有卡別：金融卡與 Richart 相關的 201 段中有 62 段沒有「信用卡」也沒有「金融卡」字樣。
  • 網頁的非主內容區塊混進別種卡的資料：Richart 信用卡頁含有簽帳金融卡的推薦區塊。
  • 名稱相近：「Richart 卡」（信用卡）和「Richart 簽帳金融卡」只差幾個字。

回答時也沒有提示詞要求模型「先確認問題講的是哪一種卡」，所以換模型只改善了其中一部分。

4. 查詢關鍵字也不同（影響沒有量）

LightRAG 會先叫模型從問題抽出關鍵字再檢索。28 題 mix 模式的關鍵字（2026-11-11 從兩個模型的 LLM 快取檔計算）中，全部由英文字母、數字、符號組成的比例：Qwen 216／279（77%），Gemma 113／199（57%）。例如 debit-confuse-01，Qwen 的關鍵字是 Taiwan New Bank、Signing account card、Handshake card，Gemma 是「台新銀行」「信用卡」「簽帳金融卡」「掛失手續費」。關鍵字不同，檢索到的段落就可能不同，所以第 1 點的差異不全是「寫答案」的差異。這次 eval 沒有存 context，影響有多大沒有量。

這份比較的限制

  • 每個模型只跑一次，沒有量同一個模型重跑的差異。2026-11-04 的紀錄裡，同一個 Qwen 在相近的 context 下有 3 題答案變差，看起來是生成不穩定。
  • ✓／△／✗ 的文字定義是依 2026-11-04 的判讀紀錄整理的，舊紀錄沒有成文定義。
  • 判讀者是語言模型，沒有人工複核。Gemma 的兩位判讀者有 6 題分歧（4 題內容分數、2 題卡別規則），由主對話裁決，裁決理由寫在各題下方。

以 Gemma 4 為最終版本時，知識庫怎麼優化

要不要用 Gemma 4 重新建立知識庫？

建議：現在不要直接全量重建，先做不用重建的改善，並用一小部分文件試建，有數據再決定。理由：

  • 目前的查詢設定下，圖譜對答案的影響小。mix 模式的 12,000 token 裡，實體與關係描述各只占 500 token，其餘都是原文段落；2026-11-04 的檢查也發現每題只對到 1～3 個實體，段落主要由向量搜尋選出。這次 Gemma 用的就是 Qwen 建的圖譜，內容 ✓ 從 8 題增加到 14 題。用 Gemma 重建圖譜，只改善那 1,000 token 的實體與關係，預期效果有限；這是推論，沒有量過。
  • 重建的成本高，風險也沒量過。上一次從頭重建 311 份文件花了約 30 小時（Qwen3-4B）。Gemma 4 匯入沒有實測過；mlx-vlm 的 embedding 路徑在匯入期間會讓 server 記憶體從 5 GB 增加到 13 GB（README 第 3 節，ticket 03 量測，當時已用 1 GB cache 上限壓制），加上 Gemma 的權重 15.3 GB，匯入時會不會超過 26 GB 的上限不知道。
  • 圖譜確實有品質問題，但不全是模型大小造成的。知識庫 17,151 個實體中有 10,926 個名稱全是英文字母、數字與符號；LightRAG 抽取提示詞裡的範例實體（Noah Carter 等）各連到 300 多個段落，而那些段落根本沒有這些字。後者看起來是小模型照抄提示詞範例，換大模型可能會改善；實體名稱用英文則可能和 LightRAG 的語言設定有關，要先查。兩者都沒驗證。

建議的順序

  1. 改回答的提示詞（不用重建）：要求先判斷問題講的是信用卡還是金融卡；問題的卡別或前提和資料不符時，第一句先指出；講權益或費用的每一段都寫出卡別；兩種卡數字不同時分開列。影響的題目：debit-wrongcard-01、debit-wrongcard-02、debit-negate-01、debit-confuse-01。改完用同一份 28 題比較。
  2. 查清楚檢索漏掉的段落（不用重建）：cross-01、cross-02 需要的卡片頁沒進 context。先存下 Gemma 的 context，看是向量搜尋沒找到、rerank 排太後面，還是 12,000 token 放不下（rerank 留 20 段，只放得進 8～10 段）。跨卡比較題可以考慮把問題拆成每張卡分別檢索再合併（.scratch/taishin-credit-card-kb/proposal-cross-card-subquestions.md）。
  3. 一次做完所有「必須重新匯入」的修改，再重建：清掉網頁的非主內容區塊（Richart 信用卡頁的金融卡推薦、金融卡頁的信用卡輪播）、在每個段落前加上卡別與卡名、查出實體名稱變英文的原因。這些都要重新匯入，所以要重建就一起做，只重建一次。
  4. 重建前先小規模試建：挑 Richart 與金融卡相關的約 40 份文件，用 Gemma 4 建到另一個 WORKING_DIR，量匯入時間與記憶體峰值，比較實體名稱的品質，以及相關題目的答案。試建證明有效、記憶體跑得動，再全量重建。

以上建議都還沒有實作。要做的話，每一項都會改變回答方式或知識庫，需要另開 spec，並用同一份 28 題比較前後結果。
