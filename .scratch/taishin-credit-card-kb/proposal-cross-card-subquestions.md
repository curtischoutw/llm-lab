# 提案：跨卡題拆成單卡子問題（方案 C，討論用，2026-11-01）

狀態：結案（2026-11-01）。實驗沒有讓跨卡類拿到 ✓（第 8 節），依第 5 節的規則不開 spec；使用者決定接受 ticket 09 的 5/7 類，不繼續做方案 C 或 D。

前一份提案是 `.scratch/taishin-credit-card-kb/proposal-answer-quality.md`，方案 C 的原始描述在它的第 3 節，第一次 probe 在第 8 節。這份提案把 C 展開成可以寫 spec 的程度。

## 1. 問題重述

- 跨卡比較類的 2 題（cross-01、cross-02），在 3 次 eval 的 mix 都沒有 ✓；加 rerank 後，cross-01 是 △，cross-02 是 ✗。
- 原因是檢索：題目同時問 3 張卡，送給 LLM 的 context 只放得下部分卡的資料。加 rerank 之後用原題只跑檢索：
  - cross-01：關鍵字句 2/3，街口聯名卡的年費資料沒有進 context；7 個 chunk 中，Gogoro 卡頁面占 5 個。
  - cross-02：關鍵字句 0/3；8 個 chunk 中，Richart 卡頁面占 4 個，活動頁占 3 個。
- 方案 C：題目裡有 2 張以上的卡時，每張卡各查一次，再合成一個答案。

### 隱含的限制

1. 單次 LLM 呼叫的 prompt 仍受 `QUERY_MAX_TOTAL_TOKENS=12000` 限制（使用者在 ticket 13 已經決定）；GPU 峰值要低於 watchdog 的 22 GB。
2. 只有一張卡的題目，查詢路徑和現在一樣，不受影響。
3. 不新增第三方套件。
4. 子查詢沿用 rerank 失敗的處理規則：任一個子查詢失敗，整個查詢就失敗，不回傳部分答案。
5. 這個方案只處理跨卡類。約定條款類（terms-01、terms-02）的原因不同，C 做完之後，ticket 09 最多到 6/7 類。

### 做完之後的不同

cross-01、cross-02 至少 1 題在 mix 拿到 ✓；其他 18 題的答案和現在相同，因為它們不會觸發拆題。

### 3.1 覆蓋：子問題的 context 合起來

| 題目 | 原題 | 手寫子問題 | 自動子問題（刪掉其他卡名） |
|---|---|---|---|
| cross-01 | 2/3 | 3/3 | 3/3 |
| cross-02 | 0/3 | 3/3 | 3/3 |

- 「自動子問題」是把原題裡其他卡名連同頓號刪掉的寫法，例如「Richart 卡的免年費辦法各是什麼？年費金額有什麼不同？」。這種寫法用規則就能產生，不需要 LLM。
- 加 rerank 之前的第一次 probe 是 cross-01 3/3、cross-02 2/3。這次 cross-02 多撈到的是「部分歐洲國家實體商店」，來自昇恆昌子問題 context 第 6 名的 chunk（`rights_notice_restricteditems.docx`）。

### 3.2 context 大小與關鍵字句的名次

- 手寫子問題：每個子查詢送進 LLM 的 chunk 合計 6,569–9,714 token，entity 加 relation 合計 362–602 token。41 個 chunk 中有 29 個是 1,200 token，最大的一個是 6,114 token（雙幣卡子問題的第 3 名）。
- 自動子問題的範圍較寬：雙幣卡只有 3 個 chunk、合計 3,892 token；entity 加 relation 合計 32–769 token。
- 3 個子查詢的 context 直接合併：cross-01 約 27,800 token、cross-02 約 26,600 token，超過 12,000 的上限。
- 單一查詢時，LightRAG 留給 chunk 的 token 實測最多 9,714（12,000 扣掉回答用的 prompt、問題、entity 與 relation）。平均分給 3 個子查詢，每個約 3,000–3,200 token，大約是前 2–3 個 chunk；遇到 6,114 token 這種大 chunk 時只放得下 1 個或放不下。
- 關鍵字句在各子查詢 context 裡的名次：
  - cross-01：街口卡的「街口商務鈦金卡」第 1 名；Gogoro 卡的「6萬」第 1 名、「首年免年費」第 1 名。
  - cross-02：雙幣卡的「2.5%」第 1 名；昇恆昌卡的「總上限2,500」第 1 名、「部分歐洲國家實體商店」第 6 名（前 6 個 chunk 合計 6,569 token）。

### 3.3 哪些題目會觸發拆題

卡名清單用 16 張卡頁的名稱，再加上簡稱（Richart、街口、Gogoro、雙幣、昇恆昌、卓富、太陽卡、玫瑰卡等）。題目裡有 2 張以上不同的卡時才觸發：

| 題目 | 比對到的卡 | 拆題 | 目前 mix |
|---|---|---|---|
| cross-01 | Richart、街口、Gogoro | 是 | △ |
| cross-02 | Richart、雙幣、昇恆昌 | 是 | ✗ |
| switch-04 | Richart（含全家Richart聯名卡）、太陽卡、玫瑰卡 | 是 | △ |
| benefit-02 | 卓富（cg045）、Richart（鈦金商務卡） | 是 | ✗ |
| benefit-01 | 昇恆昌（環球無限卡沒有自己的卡頁） | 否 | ✓ |

- 觸發的 4 題目前都沒有 ✓。
- switch-04 是誤判：reference 寫明「太陽卡／玫瑰卡（切換刷）」已更名為台新Richart卡，題目問的是哪些舊卡能用 Richart 卡的切換刷，不是比較 3 張卡。太陽卡、玫瑰卡另有自己的卡頁（cg012、cg013，指定套餐與自由選權益），所以只看卡名分不出這種情況。
- 如果卡名清單把「環球無限卡」也算成一張卡，benefit-01 就會觸發拆題。它是目前 mix 答對的題目，可能因此變差。

## 4. 方案

拆題有 3 個要決定的地方：怎麼找出卡名、子問題怎麼寫、結果怎麼合併。

### 找出卡名

- **S1 卡名清單比對**（建議）：在 rag_lab 裡維護一份「卡名或簡稱 → 卡」的對照表，題目比對到 2 張以上不同的卡就拆題。
  - 結果固定，能用單元測試驗證。
  - 缺點：新卡上架要手動加進清單。簡稱和商家名稱相同時會誤判，例如「新光三越」是卡名，也是 offer-02 問的百貨公司。
- **S2 讓 LLM 拆題**：每個查詢都多呼叫一次 LLM 判斷要不要拆。
  - 20 題都會多一次 LLM 呼叫。
  - 4B 模型在抽關鍵字時，曾輸出不合法的 JSON（第一次 probe 的雙幣卡子問題）；拆題的輸出也要能解析，同樣有這個風險。
  - 不建議。

### 子問題的寫法

- **自動寫法**（建議）：從原題刪掉其他卡名，第 3.1 節的 probe 結果是 3/3、3/3。
- 刪完之後，句子可能不通順，例如「各是什麼」只剩一張卡。從 probe 看，檢索結果沒有受影響。

### 合併

- **C1 合併 context，呼叫一次 LLM**：每個子查詢只跑檢索，把 12,000 token 平均分給各子查詢，合併後交給 LLM 回答。
  - K1：照第 3.2 節的名次，cross-01 3/3，cross-02 2/3（「部分歐洲國家實體商店」在第 6 名，會被截掉）。
  - K5：LightRAG 的 `aquery_llm` 不能直接傳入現成的 context。rag_lab 要用 `aquery_data` 取資料，自己組 context 與回答用的 prompt，等於複製 LightRAG 的 `rag_response` prompt 和 context 格式。升級 LightRAG 時要跟著檢查。
- **C2 各卡分別回答，再呼叫一次 LLM 合併答案**（建議）：每個子問題走現在的 `aquery_llm`，各自有完整的 12,000 token；最後把幾個子答案和原題交給 LLM，寫成一個答案。
  - K1：每個子查詢的 context 和 probe 相同，3/3、3/3。
  - K3：合併時的 prompt 是原題加子答案，約 2,000–5,000 token（推測，每個子答案 500–1,500 token）。
  - K4：3 張卡共 4 次 LLM 呼叫。目前每格平均 56.7–62.6 秒（第二、三次 eval，5 種模式的平均，沒有 mix 單獨的數字），所以每題約 3.8–4.2 分鐘（估計）。
  - K5：子查詢沿用現有路徑；只多一個合併用的 prompt，這個要自己寫。
  - 風險：合併時 LLM 看不到原文，只看得到子答案，所以子答案的錯誤會原樣帶過去；合併時也可能漏掉子答案裡的細節。
- **C3 各卡分別回答，直接串接**：和 C2 一樣分別回答，但不呼叫 LLM 合併，依卡名分段輸出子答案。
  - 呼叫次數最少，也沒有合併時遺漏的風險。
  - 缺點：題目問的「有什麼不同」沒有人回答。cross-01 的 reference 有比較的段落，判讀時可能只給 △。

### 分數表

| 做法 | K1 覆蓋 | K2 非跨卡題 | K3 token／記憶體 | K4 跨卡題的 LLM 次數 | K5 耦合 |
|---|---|---|---|---|---|
| S1＋C1 | 3/3、2/3 | 觸發 4 題，都不是 ✓ | ≤12,000；峰值同現在（推測） | 1 | 高：複製 prompt 與 context 格式 |
| S1＋C2 | 3/3、3/3 | 同上 | 每次 ≤12,000；峰值同現在（推測） | 4 | 低：多一個合併 prompt |
| S1＋C3 | 3/3、3/3 | 同上 | 同上 | 3 | 最低 |
| S2＋任一 | 未測 | 20 題都多一次呼叫 | 同上 | +1 | 中 |

## 5. 建議

1. 先做實驗，不改 rag_lab 程式（約 20–30 分鐘）：
   - 範圍：觸發拆題的 4 題（cross-01、cross-02、switch-04、benefit-02），用自動寫法產生子問題，在 mix 模式各自取得答案。
   - 用同一批子答案產生 C2 與 C3 兩個版本，兩位判讀者各自判讀。
   - 同時量合併時的 prompt token 數與 GPU 峰值。
2. 依結果決定：
   - C2 或 C3 讓 cross-01、cross-02 至少 1 題 ✓，而且 switch-04、benefit-02 沒有變差：用 grill-with-docs 開 spec。
   - 兩者都沒有 ✓：判讀時分清楚是子答案錯，還是合併時錯，再決定要不要繼續。
3. 約定條款類另外查原因，不放進這份 spec。

## 6. 對抗自查：最可能出錯的 3 個地方

1. **只對這 2 題有效**：卡名清單和子問題的寫法都是看著 cross-01、cross-02 設計的。
   - 能降低：實驗加進另外 2 題觸發的題目（switch-04、benefit-02）；卡名清單直接取卡頁名稱，不針對題目挑選。
   - 不能排除，寫進風險欄。
2. **合併步驟改錯數字**（C2）：benefit-03 在加 rerank 後退步，原因就是回答時寫錯次數。合併步驟多一次改寫，同類錯誤可能更多。
   - 檢驗方式：實驗時逐一比對子答案與合併答案的數字，數合併時改錯幾個。
3. **子查詢越多，查詢失敗的機會越高**：抽關鍵字時輸出不合法 JSON，查詢就會失敗。3 次 eval 共 300 格沒有發生過，probe 時發生過 1 次。
   - 每題的查詢次數從 1 次變成 3–4 次，失敗機率也大約變成 3–4 倍（推測）。
   - spec 要寫明：任一個子查詢失敗，整題就失敗（第 1 節第 4 條）。

## 7. 開 spec 時要討論的問題（下一輪 grill 用）

1. 合併用 C2 還是 C3？由實驗結果決定。
2. 卡名清單放在哪裡：寫在程式裡，還是放在設定檔？清單要不要包含沒有自己卡頁的卡（環球無限卡、昇恆昌無限卡）？已更名的舊卡名（太陽卡／玫瑰卡切換刷等 7 個）要怎麼處理？
3. 觸發條件只看「2 張以上不同的卡」，還是要再加別的條件？
4. VLM 增強查詢（`vlm_enhanced=True`）要不要也拆題？
5. 子查詢的 LLM 快取：每個子查詢會各自寫進 `:query:` 快取，合併步驟要不要快取？
6. 測試縫：沿用 CLI 子行程加 Python API，假 server 記錄收到幾次查詢、每次的問題文字。
