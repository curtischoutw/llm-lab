# Spec：增量更新知識庫

## Problem Statement

台新官網的內容會變：新活動上架、舊活動過期、權益子頁與下載區的 PDF 改版或撤下。現在要讓知識庫跟上官網，只有從頭重建一條路，實測約 30 小時。

- 下載腳本再次執行時，本地已有的檔案一律略過，不發請求。所以 `data/` 裡的檔案永遠是第一次下載的內容，已經下載的活動也不會重新判斷是否過期。
- 來源檔內容改了，匯入時會得到新的文件 ID，被當成新文件匯入；舊版本留在知識庫裡，兩個版本同時會被檢索到，答案可能把新舊規則混在一起。
- 來源檔不在了（活動過期、官網撤下），知識庫裡的文件不會消失，仍會被檢索到。
- 知識庫變了之後再問同一題，LightRAG 的查詢快取直接回傳舊答案，因為快取鍵不含檢索到的內容。
- LightRAG 的文件狀態只記檔名、不記路徑，rag_lab 也沒有記，所以目前無從得知某份來源檔對應知識庫裡的哪個版本。

## Solution

分成兩段，兩段都可以單獨使用：

1. **下載腳本的更新模式**：重新檢查官網。內容有變的檔案才覆寫，沒變的檔案完全不碰；官網上已經沒有的、過期的，搬到 `_meta/removed/<日期>/`。
2. **匯入端的同步**：`ingest <資料夾>` 對照 rag_lab 自己記的「路徑 → 文件 ID」對照表：
   - 新的文件照常匯入；
   - 內容變了的文件，先匯入新版本，成功後刪掉舊版本；
   - 沒變的略過；
   - 之前從這個資料夾匯入、現在檔案不在的文件，只列出來；加 `--prune` 才從知識庫刪掉。

   知識庫有任何改動時，自動清掉查詢的答案快取。

使用者照「備份 → 逐一 `ingest` 6 個資料夾建好對照表 → 更新模式下載 → 再逐一 `ingest` → 看『來源已不在』清單 → `--prune`」的順序，就能讓知識庫跟上官網，不用重建。

## Implementation Decisions

### 詞彙

- 依 GLOSSARY：**文件**以路徑認定，同一個路徑的內容改了仍是同一份文件；改名或搬位置算移除一份、新增一份。**版本**是一份文件某次匯入時的內容，以文件 ID 區分；知識庫裡同一份文件只有一個版本。兩份文件內容相同時共用同一個版本（文件 ID 只由解析後的內容算出）。
- 「知識庫有改動」指這次處理對 LightRAG 的儲存做了寫入或刪除（不論那份文件最後成功或失敗）。判準：解析完成、開始把內容寫進 LightRAG 之後（不論在哪一步失敗），或呼叫過刪除，都算有改動；解析階段（MinerU、LibreOffice）就失敗、沒有寫入任何內容的，不算。報告分類是從文件的角度看，兩者不一定一致：例如內容和別的路徑相同的新路徑，報告記「新增」，但知識庫沒有改動。

### 下載腳本：更新模式

- 新增一個命令列選項開啟更新模式；不開時行為不變。下載腳本的模組說明同步改寫：目前寫的「要更新內容時刪除資料夾後重新下載」，以及已知極限裡的「已存在的活動不重新判斷是否過期」「要刪 `_meta/html` 才會重新下載」，都要改成區分有沒有開更新模式的說法。
- 下載資料夾的結構不變：各類別的文件在 `DIR/<類別資料夾>/`，原始 HTML 在 `DIR/_meta/html/`，列印用的本機 HTML 在 `DIR/_meta/print/`，下載清單在 `DIR/_meta/manifest.jsonl`。`_meta` 在資料根目錄，不在類別資料夾底下。
- 變更判斷：
  - 網頁類（卡片頁、權益子頁、活動頁）：重新取得原始 HTML，和 `DIR/_meta/html/` 裡存的上一份比對；不同才重新轉檔。基準是存檔本身，不是下載清單：下載清單每次執行整份重寫，只含這次處理到的文件。
  - 存檔的原始 HTML 在、文件不在（現有流程先存原始 HTML 再轉檔，第一次下載時轉檔失敗會留下這種狀態）：不比對，照新增處理並轉檔，成功記「已下載」。例外是存檔 HTML 讀出的活動期間已過期的活動，照現行規則記「過期略過」，不轉檔（見下面的過期判斷）。
  - 轉檔成功後，才換掉存檔的原始 HTML、列印用的本機 HTML 與文件；轉檔失敗時三者都不動，下次執行會再比對到差異並重試。
  - 原檔類（下載區 PDF、權益附件）：先下載到暫存位置，比對檔案的雜湊，不同才換掉；下載失敗時原檔不動。
  - 沒變的檔案不重寫，修改時間不動。RAG-Anything 1.4.3 的解析快取鍵含檔案的絕對路徑、修改時間與內容雜湊，重寫就會讓快取失效、重跑 MinerU。
- 實作第一步先實測（grill Q28）：用 2026-10-30 存下的 `DIR/_meta/html/`（主 checkout 的 `data/taishin_credit_card/_meta/html/`；`data/` 不進 git，worktree 裡沒有），卡片頁、權益子頁、活動頁各取 2 頁，和現在的頁面比對原始 HTML。結果與指令寫進 ticket。差異只出現在主內容區以外（導覽、頁尾、計數器、token 等）時，網頁類的比對（ticket 07）先停下來，由使用者決定是否改成只比主內容區；下載區 PDF 的部分（ticket 06）不受影響，照常完成。對官網的請求遵守現有的請求間隔。
- 下架判斷：
  - 列表類（卡片、權益子頁、下載區、活動）：這次的列表裡沒有、本地有的文件，算下架。
  - 權益附件：所有權益子頁都不再連到它，才算下架（現行規則同一個網址只下載一次）。附件的候選與下架判斷讀權益子頁存檔的原始 HTML（和現行做法相同）；子頁內容變了但轉檔失敗時存檔不換，所以「權益子頁沒有成功取得」包含請求失敗與轉檔失敗兩種，這次不判斷附件下架，下次轉檔成功後再判斷。
  - 某個類別的列表頁沒有成功取得時，那個類別不搬任何檔案。列表頁回應成功、但解析出 0 筆而本地有這個類別的文件時，也當成列表頁沒有成功取得（防止官網改版讓解析失效時搬走整個類別）。依賴它的類別也不搬：權益列表或任何一個權益子頁沒有成功取得時，這次不判斷附件下架；活動列表沒有成功取得時，這次不判斷活動過期與活動圖片下架（grill Q11、Q27 的延伸）。報告寫明原因。
- 活動圖片（grill Q18、Q26）：
  - 圖片與活動的對應，從活動存下來的原始 HTML 算出（主視覺網址 → 圖片檔；圖片的檔名來自主視覺網址）。在活動的過期、下架與內容變更都處理完之後算：圖片資料夾裡的圖片，沒有任何一個「活動文件仍在」的活動的存檔 HTML 指向它時，搬走。所以兩個活動共用同一張圖時，兩個活動都過期或下架才搬走；活動改版換了主視覺網址時，舊圖也搬走（轉檔失敗時存檔不換，舊圖保留到下次）。
  - 仍有效、主視覺網址沒變、已有圖片的活動，不重新請求它的圖片，圖片不換。主視覺網址變了的仍有效活動，舊圖照上一條搬走，新的主視覺照下面的補名額規則下載，而且排在其他候選之前。
  - 只有原始 HTML、沒有活動文件的活動（期間已過期而略過的），它的 HTML 不算在「活動文件仍在」裡；現行規則不替這類活動下載圖片，所以不會有它們的圖片要搬。
  - 名額的算法：在「活動文件仍在」的活動的主視覺網址中去除重複後，圖片檔在本地存在的，或副檔名不支援的（從網址判斷，現行規則照樣佔名額），各佔一個名額。下載失敗、沒有留檔的不佔名額。
  - 只在名額少於 8 個時補：依活動被找到的順序，從「活動文件確實存在、有主視覺、主視覺網址還沒有佔名額」的活動補，補到 8 個或沒有候選為止。和已佔名額的活動共用同一個主視覺網址的活動，不是候選。新出現在前面的活動不擠掉現有的圖片。
- 過期判斷（grill Q8、Q27）：
  - 更新模式對每個已有活動文件的活動重新判斷（現有規則：結束日早於下載當天才算過期），過期的搬走。同一次既內容變更又過期的，記為過期移除。
  - 只有原始 HTML、沒有活動文件的活動：從存檔 HTML 讀出的期間已過期時，照現行規則記「過期略過」，不轉檔、不請求詳情頁，維持現狀；沒有過期（或期間不明）時，照上面「原始 HTML 在、文件不在」的規則當成新增轉檔。磁碟上沒有第一次下載的紀錄，所以只能用期間判斷。
- 搬移：文件連同它在 `DIR/_meta/html/`、`DIR/_meta/print/` 的檔案，搬到 `DIR/_meta/removed/<日期>/`，底下保留原本的相對路徑：文件到 `<類別資料夾>/<檔名>`，原始 HTML 與列印用 HTML 照原本的扁平存放，到 `html/<名稱>.html`、`print/<名稱>.html`（`_meta/html/`、`_meta/print/` 底下沒有類別子資料夾）。`_meta` 不會被匯入。ASSUMPTION：目的地已有同名檔時，在檔名後加時間，不覆寫。同一份文件之後重新上架，視為新增（ASSUMPTION）。
- ASSUMPTION：下載清單新增結果值（內容變更、未變、下架、過期移除；中文標籤由實作決定，風格與現有的一致）；更新模式下新出現的文件沿用現有的「已下載」。結束時印出各類別、各結果的數量。
- 請求間隔、網域限制、轉址規則與現有模式相同，更新模式也要有驗收條件確認請求間隔。

### 匯入端：對照表

- 檔名與格式（定下來是為了讓測試能造出各種狀態，測試可以讀寫這個檔）：`WORKING_DIR/rag_lab_documents.json`，內容是

  ```json
  {"version": 1, "documents": {"<文件的絕對路徑>": {"doc_id": "doc-…", "ingested_at": "<ISO 8601>", "source_folder": "<絕對路徑>"}}}
  ```

- 路徑一律用 CLI 現行的方式取絕對路徑（`resolve()`，symlink 會被解析成實體路徑）。Python API 收到的路徑也照同樣方式處理。
- 來源資料夾：`ingest <資料夾>` 時記那個資料夾；匯入單一檔案時記該檔案所在的資料夾（ASSUMPTION：所以之後對那個資料夾 `--prune` 時，這份文件也在檢查範圍內）。Python API 指定了來源資料夾時記指定的資料夾；沒指定時記檔案所在的資料夾。
- 寫入：每份文件處理成功（新增、替換、沒變而略過）後更新該筆；先寫暫存檔再改名，避免寫到一半的檔案。ASSUMPTION：對照表寫入失敗讓這次 ingest 失敗，不吞掉。對照表存在但內容不是合法的 JSON 或格式不符時，ingest 在處理任何文件之前失敗並指出檔案路徑，不當成空表（CLI 結束碼 1，Python API 拋 `PipelineError`；寫入失敗相同）。沒有對照表時視為空表。
- 每份文件匯入時都會先解析（走解析快取）取得這次的文件 ID，再依下面的順序判斷：
  1. 對照表有這個路徑、記的 ID 等於這次的 ID：
     - 已完整匯入 → 沒變。
     - 沒有完整匯入或不在知識庫（例如先前失敗、或重匯調查刪掉了它）→ 照一般匯入（含現行的「清掉舊紀錄再重匯」），成功記「新增」。
  2. 對照表有這個路徑、記的 ID 不等於這次的 ID：
     - 這次的 ID 已完整匯入（上次替換中斷：新版本已匯入、舊版本沒刪）→ 補刪舊 ID，記「替換」。
     - 記的 ID 已不在知識庫 → 照一般匯入新版本，不刪任何東西，記「新增」。
     - 其他 → 替換（見下一節），記「替換」。替換失敗後下次重試成功，同樣記「替換」。
  3. 對照表沒有這個路徑（遷移：對照表建立前匯入的文件，或新的路徑）：
     - 這次的 ID 已完整匯入，而且沒有別的路徑對照到它 → 沒變，補上對照表（現有知識庫第一次建對照表的情況）。
     - 這次的 ID 已完整匯入，而且已對照到別的路徑 → 新增（共用版本），補上對照表；知識庫沒有改動。
     - 否則用檔名到 LightRAG 的文件狀態找已完成的文件，排除已對照到別的路徑的 ID：剛好一份 → 當作舊版本並替換；0 份 → 新增（grill Q22）；多份 → 不替換也不新增，記成失敗，訊息列出候選的文件 ID。
- 實機第一次同步前，要先對各資料夾跑一次 `ingest` 建好對照表，再跑下載端的更新模式（grill Q19）：否則更新模式搬走的文件在對照表裡沒有紀錄，`--prune` 找不到它們。

### 匯入端：替換與移除

- 替換順序：匯入新版本 → 成功後刪舊版本（保留 LLM 抽取快取）→ 更新對照表。
- 替換時新版本匯入失敗（grill Q23、Q25）：刪掉新版本已經寫進知識庫的部分（例如圖、表、公式描述失敗時已寫入的文字 chunk 與實體），而且不為它留下失敗紀錄（現行流程在整批結束後會替描述失敗的文件補記失敗狀態，替換失敗的新版本要排除在外，否則刪掉的紀錄會被重建）。舊版本與對照表不變，報告記成失敗並說明舊版本仍在。清除寫了一半的部分本身失敗時，報告寫出兩個文件 ID 與原因，結束碼 1；下次 ingest 依對照表規則重試。
- 新文件（不是替換）匯入失敗：維持現行行為，保留失敗紀錄，下次 ingest 先清掉再重匯。
- 刪除前先查對照表：還有別的路徑指向同一個文件 ID 時，不刪知識庫的內容，只移除（或改寫）這個路徑的那一筆。替換的舊版本與 `--prune` 都適用。這種 `--prune` 在報告仍記「已刪除」。
- ASSUMPTION：刪舊版本失敗時記成失敗，訊息寫出新舊兩個文件 ID，結束碼 1；下次 ingest 依規則 2 補刪。
- 移除：只在指定了來源資料夾時檢查（CLI 的 `ingest <資料夾>`、Python API 指定來源資料夾），對象是對照表裡來源資料夾等於這個資料夾、路徑在檔案系統上已不存在的文件。沒有 prune 時只列在報告；有 prune 時逐一刪除並移除對照表那一筆。
- 資料夾不存在或已經沒有任何支援的文件時，不做移除（grill Q24：防止路徑打錯時刪光一個資料夾的文件）：CLI 照現行規則以結束碼 2 結束（不論有沒有 `--prune`）；Python API 指定了來源資料夾、而那個資料夾不存在或沒有任何支援的文件時，同樣拋使用錯誤（不論有沒有給 prune），和 CLI 相同。
- 匯入單一檔案時不檢查移除；替換照常做。
- 刪除一律保留 LLM 抽取快取。

### 匯入端：答案快取

- 每份文件處理完，只要那份文件的處理對知識庫做了寫入或刪除（不論最後成功或失敗，含替換失敗後的清除、`--prune` 的刪除），就立刻清掉 LLM 快取裡所有查詢答案（cache type 為 query）的項目，保留查詢關鍵字的項目與匯入用的抽取快取（grill Q4、Q25）。不在整批結束時才清：行程中途被停掉時，已經改動的部分也已經清過。
- 不用 LightRAG 清全部快取的功能（它會連關鍵字與抽取快取一起清），要只清查詢答案的項目。
- 知識庫沒有改動的文件（沒變、共用版本的新增或刪除）不觸發清除。
- ASSUMPTION：這次 ingest 清掉的筆數寫進報告。

### 匯入端：介面

- CLI：`ingest` 新增 `--prune` 選項。ASSUMPTION：指定單一檔案加 `--prune` 時以結束碼 2 結束並說明原因（和其他使用錯誤相同）。
- 報告：現有的每份文件報告與統計保留，另外分類列出新增、替換、沒變、來源已不在（未刪，列出路徑）、已刪除、失敗的數量與清單，以及清掉的答案快取筆數。每份文件只歸一類：加 prune 且刪除成功的只算「已刪除」。
- 結束碼：「來源已不在（未刪）」不影響結束碼（沒有其他失敗時為 0）；有任何一份記「失敗」時為 1，和現行規則相同。
- Python API：模組函式與 `Session` 的 ingest 新增兩個 keyword 參數：來源資料夾（預設無，即不檢查移除）與 prune（預設否）。ingest 的回傳結果新增上面各分類。
- ASSUMPTION：參數名稱與型別由實作決定；沒有來源資料夾卻給 prune 時，拋和現有使用錯誤相同類型的例外。CLI 與 Python API 的行為必須相同。

## Testing Decisions

- 好的測試只看外部行為：結束碼、CLI 輸出、Python API 的回傳值與例外、產生的檔案（下載資料夾、`_meta/removed/`、下載清單、對照表）。不測內部函式，不直接讀 LightRAG 的儲存檔來斷言。答案快取是否被清，透過「同一題再問會不會重新呼叫假 LLM」觀察。
- 對照表的檔名與格式是公開的契約，測試可以先寫好對照表來造出「替換中斷」「對照表記的 ID 不在知識庫」「沒有對照表」等狀態；知識庫端的故障用假 server 注入（例如讓描述或 embedding 回錯誤）。
- 縫（使用者在 grill Q16 確認）：
  - 匯入端：CLI 子行程＋Python API（子行程內呼叫 rag_lab 的模組函式與 `Session`），搭配現有的假 OpenAI server、假 mineru。
  - 下載端：下載腳本的子行程，搭配現有的假 HTTP server、假 Chrome、假 LibreOffice。
  - 不新增其他縫。
- 要涵蓋的行為：
  - 下載端：沒變的檔案修改時間不變；HTML 變了才重新轉檔；轉檔失敗時存檔的 HTML 與文件都不變；PDF 內容變了才換；列表少了一份 → 搬到 `DIR/_meta/removed/<日期>/` 並保留相對路徑；列表頁失敗 → 那個類別與依賴它的類別都不搬；附件只在所有子頁都不連到時才下架；活動過期 → 搬走，圖片照對應搬走、只在名額不足時補；仍有效活動的圖片不重新請求；第一次下載就過期的活動不處理；請求間隔；不開更新模式時行為不變（既有測試全綠）。
  - 匯入端：對照表三條規則的每個分支；替換（查詢只看到新內容）；替換時新版本失敗（寫入一半的內容被刪、沒有留下失敗紀錄、舊版本仍在、答案快取被清）；替換中斷後補刪舊版本；兩個路徑內容相同時刪其中一個不影響另一個；來源已不在只列出；prune 只刪該資料夾的；單一檔案不檢查移除；單一檔案加 `--prune` 結束碼 2；Python API 指定的來源資料夾不存在或沒有支援的文件時拋使用錯誤；對照表壞掉時失敗；有改動的文件處理完答案快取就被清、沒改動時不清；關鍵字快取與抽取快取保留。
- 先例：`tests/test_pipeline.py` 的重複匯入、失敗重試與大表格切表測試；`tests/test_python_api.py` 的 `Session` 測試；`scripts/test_fetch_taishin.py` 的過期判斷與再次執行略過測試。
- 實機驗收（主對話執行，排在截斷調查之後；順序經 grill Q19 修改）：備份 `rag_storage` → 6 個資料夾逐一 `ingest` 建對照表（預期全部沒變）→ 對官網跑更新模式 → 6 個資料夾逐一 `ingest`（不加 `--prune`）→ 「來源已不在」清單給使用者確認 → `--prune` → 抽題 eval 確認答案用到新內容。ASSUMPTION：eval 用 mix 模式；記錄各類別的變動數量、耗時、GPU 記憶體峰值。

## Out of Scope

- 定期或排程自動更新。
- 內容沒變、但處理規則變了的文件（例如 ticket 12 之前匯入、沒有切表的 22 份）：文件 ID 相同，同步視為沒變。這一類由 `.scratch/chunk-truncation/` 的重匯處理。
- 清理 LLM 抽取快取的大小。
- 台新以外的下載來源（論文、多格式文件）的更新模式；匯入端的同步對任何資料夾都適用。
- 改名或搬位置時保留原本的版本：照 GLOSSARY，視為移除一份、新增一份。
- 查詢快取以外的快取失效（例如解析快取）：解析快取鍵本來就含內容雜湊與修改時間。
- 用 `--prune` 刪掉整個已不存在的資料夾的文件（grill Q24）。
