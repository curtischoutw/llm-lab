# Spec：增量更新知識庫

## Problem Statement

台新官網的內容會變：新活動上架、舊活動過期、權益子頁與下載區的 PDF 改版或撤下。現在要讓知識庫跟上官網，只有從頭重建一條路，實測約 30 小時。

- 下載腳本再次執行時，本地已有的檔案一律略過，不發請求。所以 `data/` 裡的檔案永遠是第一次下載的內容，已經下載的活動也不會重新判斷是否過期。
- 來源檔內容改了，匯入時會得到新的文件 ID，被當成新文件匯入；舊版本留在知識庫裡，兩個版本同時會被檢索到，答案可能把新舊規則混在一起。
- 來源檔不在了（活動過期、官網撤下），知識庫裡的文件不會消失，仍會被檢索到。
- 知識庫變了之後再問同一題，LightRAG 的查詢快取直接回傳舊答案，因為快取鍵不含檢索到的內容。
- LightRAG 的文件狀態只記檔名、不記路徑，rag_lab 也沒有記，所以目前無從得知某份來源檔對應知識庫裡的哪個版本。

## Solution

分成兩段，兩段都可以單獨使用：

1. **下載腳本的更新模式**：重新檢查官網。內容有變的檔案才覆寫，沒變的檔案完全不碰；官網上已經沒有的、過期的，搬到 `_meta/removed/<日期>/`。
2. **匯入端的同步**：`ingest <資料夾>` 對照 rag_lab 自己記的「路徑 → 文件 ID」對照表：
   - 新的文件照常匯入；
   - 內容變了的文件，先匯入新版本，成功後刪掉舊版本；
   - 沒變的略過；
   - 之前從這個資料夾匯入、現在檔案不在的文件，只列出來；加 `--prune` 才從知識庫刪掉。

   知識庫有任何改動時，自動清掉查詢的答案快取。

使用者照「備份 → 逐一 `ingest` 6 個資料夾建好對照表 → 更新模式下載 → 再逐一 `ingest` → 看『來源已不在』清單 → `--prune`」的順序，就能讓知識庫跟上官網，不用重建。

## User Stories

### 下載端

1. As a 知識庫維護者, I want 下載腳本有一個更新模式, so that 不刪資料夾也能讓 `data/` 跟上官網。
2. As a 知識庫維護者, I want 更新模式只覆寫內容真的變了的檔案, so that 沒變的文件下次匯入時走解析快取，不重跑 MinerU。
3. As a 知識庫維護者, I want 沒變的檔案連修改時間都不動, so that 解析快取鍵（含修改時間）不會因為重新寫入而失效。
4. As a 知識庫維護者, I want 卡片頁、權益子頁、活動頁用原始 HTML 的雜湊判斷有沒有變, so that 轉檔產生的位元組差異不會被誤判成內容變更。
5. As a 知識庫維護者, I want 下載區的 PDF 與權益附件用檔案本身的雜湊判斷有沒有變, so that 官網換掉 PDF 內容時會被偵測到。
6. As a 知識庫維護者, I want 內容變了的 PDF 先下載到暫存位置、比對後才換掉原檔, so that 下載失敗時原檔還在。
7. As a 知識庫維護者, I want 官網列表裡已經沒有的文件被搬到 `_meta/removed/<日期>/`, so that 匯入端看得到它不在了，檔案本身也還查得到。
8. As a 知識庫維護者, I want 更新模式重新判斷每個活動是否過期, so that 過期活動不再留在 `data/` 裡。
9. As a 知識庫維護者, I want 過期的活動也搬到 `_meta/removed/<日期>/`, so that 過期與下架用同一種方式處理。
10. As a 知識庫維護者, I want 某個類別的列表頁抓取失敗時，那個類別這次不搬任何檔案, so that 一次網路錯誤不會讓整個類別被當成全部下架。
11. As a 知識庫維護者, I want 有權益子頁抓取失敗時，這次不判斷附件下架, so that 附件不會因為子頁暫時打不開而被當成下架。
12. As a 知識庫維護者, I want 所有權益子頁都不再連到的附件被當成下架, so that 撤下的附件也會離開知識庫。
13. As a 知識庫維護者, I want 活動圖片跟著它的活動：活動過期或下架，圖片也搬走；總數少於 8 個時才從後面的活動補上, so that 圖片的數量與規則和第一次下載相同。
14. As a 知識庫維護者, I want 仍然有效的活動，它的圖片不重新請求、不換, so that 沒變的圖片不需要重新匯入。
15. As a 知識庫維護者, I want 下載清單記下每份文件這次的結果（新增、內容變更、未變、下架、過期、失敗）, so that 我知道這次改了哪些檔案。
16. As a 知識庫維護者, I want 更新模式結束時印出各類別、各結果的數量, so that 不用讀清單也能看出變動規模。
17. As a 知識庫維護者, I want 更新模式仍然遵守請求間隔, so that 對官網的負擔和第一次下載相同。
18. As a 知識庫維護者, I want 不加更新模式時，下載腳本的行為和現在完全相同, so that 第一次下載與既有的測試不受影響。

### 匯入端

19. As a 知識庫維護者, I want rag_lab 在知識庫的資料夾裡記一份「路徑 → 文件 ID、匯入時間、來源資料夾」的對照表, so that 能判斷某個路徑上的文件是新的、變了，還是沒變。
20. As a 知識庫維護者, I want 對照表跟著 `WORKING_DIR` 走, so that 換一個知識庫就換一份對照表，不會互相干擾。
21. As a 知識庫維護者, I want 同一個路徑的內容變了時，知識庫裡只留下新版本, so that 查詢不會同時檢索到新舊兩個版本。
22. As a 知識庫維護者, I want 替換時先匯入新版本、成功後才刪舊版本, so that 新版本匯入失敗時知識庫不會少一份文件。
23. As a 知識庫維護者, I want 新版本匯入失敗時，寫進一半的新內容被刪掉，報告寫出失敗原因並說明舊版本仍在, so that 知識庫不會同時有新舊兩個版本，我也知道這份文件還是舊內容。
24. As a 知識庫維護者, I want 沒變的文件照常略過、不呼叫模型, so that 同步的時間和變動量成正比。
25. As a 知識庫維護者, I want `ingest <資料夾>` 列出「之前從這個資料夾匯入、現在檔案不在」的文件，但不刪, so that 我先看清單再決定。
26. As a 知識庫維護者, I want 加上 `--prune` 才刪掉這些文件，而且只刪之前從這個資料夾匯入的, so that 指錯資料夾也不會刪到別的資料夾的文件。
27. As a 知識庫維護者, I want 匯入單一檔案時不檢查移除, so that 匯入一份文件不會牽動其他文件。
28. As a 知識庫維護者, I want 對照表在匯入時順便補上、不需要另外的遷移指令, so that 現有的 311 份文件跑一次同步就有紀錄。
29. As a 知識庫維護者, I want 對照表裡沒有的路徑內容變了時，rag_lab 用檔名去文件狀態找舊版本，剛好一份才採用, so that 現有的文件也能被替換。
30. As a 知識庫維護者, I want 用檔名找到 0 份或多份時，那份文件不替換、列在報告裡, so that rag_lab 不會猜錯而刪掉別份文件。
31. As a 知識庫維護者, I want 報告分成新增、替換、沒變、來源已不在（未刪）、已刪除、失敗, so that 我看得出這次同步做了什麼。
32. As a Python API 使用者, I want `IngestSummary` 有同樣的分類, so that 程式也能判斷同步結果。
33. As a Python API 使用者, I want Python API 也能指定來源資料夾與 `prune`, so that 程式裡的同步和 CLI 行為相同。
34. As a 提問的人, I want 知識庫有新增、替換或刪除時，答案快取自動清掉, so that 同一題會用新的知識庫重新回答。
35. As a 提問的人, I want 關鍵字快取保留, so that 只依賴問題文字的關鍵字不用重抽。
36. As a 知識庫維護者, I want 知識庫沒有任何改動時（全部沒變），答案快取不清, so that 單純重跑同步不會讓下一次查詢變慢。
37. As a 知識庫維護者, I want 刪除舊版本時保留它的抽取快取, so that 新舊版本內容相同的 chunk 不用重新呼叫 LLM。
38. As a 知識庫維護者, I want 刪除或替換失敗時報告寫出原因、結束碼非 0, so that 我知道知識庫可能處在不一致的狀態。
39. As a 知識庫維護者, I want 替換做到一半中斷（新版本已匯入、舊版本沒刪）時，下次 ingest 自動補刪舊版本, so that 舊版本不會永遠留在知識庫。
40. As a 知識庫維護者, I want 兩個路徑內容相同、共用同一個版本時，刪其中一個路徑不影響另一個, so that 替換或 `--prune` 不會刪掉別的文件還在用的內容。
41. As a 知識庫維護者, I want 資料夾不存在或已經沒有文件時，`ingest --prune` 不做任何刪除, so that 路徑打錯不會刪光一個資料夾的文件。

### 實機驗收

42. As a 知識庫維護者, I want 實機驗收前先備份整個 `rag_storage`, so that 同步出錯時可以回到原狀。
43. As a 知識庫維護者, I want 第一次跑更新模式前，先對各資料夾 ingest 一次建好對照表, so that 更新模式搬走的文件之後能被 `--prune` 找到。
44. As a 知識庫維護者, I want 驗收時先不加 `--prune` 跑一輪，把「來源已不在」的清單給我確認, so that 刪除前有人看過。
45. As a 知識庫維護者, I want 驗收後抽題確認答案用到新內容, so that 確認同步真的改變了查詢結果。

## Implementation Decisions

### 詞彙

- 依 GLOSSARY：**文件**以路徑認定，同一個路徑的內容改了仍是同一份文件；改名或搬位置算移除一份、新增一份。**版本**是一份文件某次匯入時的內容，以文件 ID 區分；知識庫裡同一份文件只有一個版本。兩份文件內容相同時共用同一個版本（文件 ID 只由解析後的內容算出）。

### 下載腳本：更新模式

- 新增一個命令列選項開啟更新模式；不開時行為不變。
- 變更判斷：
  - 網頁類（卡片頁、權益子頁、活動頁）：重新取得原始 HTML，和類別資料夾 `_meta/html/` 裡存的上一份原始 HTML 比對；不同才重新轉檔。基準是存檔本身，不是下載清單：下載清單每次執行整份重寫，只含這次處理到的文件。
  - 轉檔成功後，才換掉存檔的原始 HTML 與文件；轉檔失敗時兩者都不動，下次執行會再比對到差異並重試。
  - 原檔類（下載區 PDF、權益附件）：先下載到暫存位置，比對檔案的雜湊，不同才換掉；下載失敗時原檔不動。
  - 沒變的檔案不重寫，修改時間不動。RAG-Anything 1.4.3 的解析快取鍵含檔案的絕對路徑、修改時間與內容雜湊，重寫就會讓快取失效、重跑 MinerU。
- 實作第一步先實測，結果與指令寫進 ticket：(a) 同一個網頁抓兩次，原始 HTML 是否相同；(b) 同一份 HTML 用 Chrome headless 列印兩次、用 LibreOffice 轉兩次，位元組是否相同。不論 (b) 的結果，網頁類都比原始 HTML。若 (a) 顯示原始 HTML 每次都不同（例如含時間戳或 token），停下來回報，比對規則由使用者決定。
- 下架判斷：
  - 列表類（卡片、權益子頁、下載區、活動）：這次的列表裡沒有、本地有的文件，算下架。
  - 權益附件：所有權益子頁都不再連到它，才算下架（現行規則同一個網址只下載一次）。
  - 某個類別的列表頁沒有成功取得時，那個類別不搬任何檔案；有任何一個權益子頁沒有成功取得時，這次不判斷附件下架（ASSUMPTION：附件可能被多頁連到，無法只看單一頁）。報告寫明原因。
- 活動圖片：
  - 仍有效、且已有圖片的活動，不重新請求它的圖片，圖片不換。
  - 活動過期或下架時，它的圖片跟著搬走。
  - 只在總數少於 8 個時補：依活動被找到的順序，從「活動文件確實存在、有主視覺、還沒有圖片」的活動補上，補到 8 個或沒有候選為止。新出現在前面的活動不會擠掉現有的圖片。
- 過期判斷：更新模式對每個活動重新判斷（現有規則：結束日早於下載當天才算過期），過期的搬走。
- 搬移：文件連同它在 `_meta` 底下的原始 HTML 與列印用的暫存，搬到該類別資料夾的 `_meta/removed/<日期>/`；`_meta` 不會被匯入。ASSUMPTION：目的地已有同名檔時，在檔名後加時間，不覆寫。同一份文件之後重新上架，視為新增（ASSUMPTION）。
- ASSUMPTION：下載清單新增結果值（內容變更、未變、下架、過期移除；中文標籤由實作決定，風格與現有的「已下載」「已存在略過」一致），結束時印出各類別、各結果的數量。
- 請求間隔、網域限制、轉址規則與現有模式相同。

### 匯入端：對照表

- 存成 `WORKING_DIR` 裡的一個 JSON 檔，由 rag_lab 讀寫。每筆以文件的絕對路徑為鍵，值含文件 ID、匯入時間、來源資料夾。
- ASSUMPTION：匯入單一檔案時，來源資料夾記為該檔案所在的資料夾；所以之後對那個資料夾 `--prune` 時，這份文件也在檢查範圍內。
- 用絕對路徑：文件 ID 本來就含圖片的絕對路徑，專案搬位置時要重建知識庫（README 搬機器一節），對照表跟著重建。
- 寫入時機：每份文件處理成功（新增、替換、沒變而略過）後更新該筆。ASSUMPTION：對照表寫入失敗讓這次 ingest 失敗，不吞掉。
- 每份文件匯入時都會先解析（走解析快取）取得這次的文件 ID，再依下面的順序判斷：
  1. 對照表有這個路徑、記的 ID 等於這次的 ID，且已完整匯入 → 沒變。
  2. 對照表有這個路徑、記的 ID 不等於這次的 ID → 替換（見下一節）。這次的 ID 已經完整匯入時（上次替換中斷，新版本已匯入、舊版本沒刪），只補刪舊 ID，報告仍記為「替換」。對照表記的 ID 已經不在知識庫時，不刪任何東西，只更新對照表。
  3. 對照表沒有這個路徑（遷移：對照表建立前匯入的文件，或新文件）：
     - 這次的 ID 已完整匯入 → 沒變，補上對照表。
     - 否則用檔名到 LightRAG 的文件狀態找已完成的文件，排除已經對照到別的路徑的 ID：剛好一份 → 當作舊版本並替換；0 份 → 新增（匯入端無法分辨新文件與舊版本已不在；使用者在 grill Q22 同意）；多份 → 不替換也不新增，記成失敗，訊息列出候選的文件 ID。
- 沒有對照表時視為空表。實機第一次同步前，要先對各資料夾跑一次 `ingest` 建好對照表，再跑下載端的更新模式（grill Q19）：否則更新模式搬走的文件在對照表裡沒有紀錄，`--prune` 找不到它們。

### 匯入端：替換與移除

- 替換順序：匯入新版本 → 成功後刪舊版本（保留 LLM 抽取快取）→ 更新對照表。
- 新版本匯入失敗：刪掉新版本已經寫進知識庫的部分（例如圖、表、公式描述失敗時已寫入的文字 chunk 與實體），舊版本與對照表不變，記成失敗。知識庫沒有改動。
- 刪除前先查對照表：還有別的路徑指向同一個文件 ID 時，不刪知識庫的內容，只移除（或改寫）這個路徑的那一筆。替換的舊版本與 `--prune` 都適用。
- ASSUMPTION：刪舊版本失敗時記成失敗，訊息寫出新舊兩個文件 ID，結束碼 1；下次 ingest 依上一節的規則 2 補刪。
- 移除：只在 `ingest <資料夾>` 時檢查，對象是對照表裡來源資料夾等於這個資料夾、路徑已不存在的文件。沒有 `--prune` 時只列在報告；有 `--prune` 時逐一刪除並移除對照表那一筆。
- 資料夾不存在或已經沒有任何支援的文件時，`ingest` 照現行規則以結束碼 2 結束，不做移除（grill Q24：防止路徑打錯時刪光一個資料夾的文件）。
- 匯入單一檔案時不檢查移除；替換照常做。
- 刪除一律保留 LLM 抽取快取。

### 匯入端：答案快取

- 一次 ingest 裡只要有新增、替換或刪除成功（含先前失敗的文件這次重試成功），結束前清掉 LLM 快取裡所有查詢答案的項目，保留查詢關鍵字的項目與匯入用的抽取快取。全部沒變、或只有失敗（失敗時已刪掉寫入一半的內容）時不清。
- ASSUMPTION：清除的筆數寫進報告。

### 匯入端：介面

- CLI：`ingest` 新增 `--prune` 選項。ASSUMPTION：指定單一檔案加 `--prune` 時以結束碼 2 結束並說明原因（和其他使用錯誤相同）。
- 報告：現有的每份文件報告與統計保留，另外分類列出新增、替換、沒變、來源已不在（未刪，列出路徑）、已刪除、失敗的數量與清單，以及清掉的答案快取筆數。每份文件只歸一類：加 `--prune` 且刪除成功的只算「已刪除」，不再算「來源已不在」。
- Python API：模組函式與 `Session` 的 ingest 新增兩個 keyword 參數：來源資料夾（預設無，即不檢查移除）與 prune（預設否）。ingest 的回傳結果新增上面各分類。
- ASSUMPTION：參數名稱與型別由實作決定；沒有來源資料夾卻給 prune 時，拋和現有使用錯誤相同類型的例外。CLI 與 Python API 的行為必須相同。

## Testing Decisions

- 好的測試只看外部行為：結束碼、CLI 輸出、Python API 的回傳值與例外、產生的檔案（下載資料夾、`_meta/removed/`、下載清單）。不測內部函式，不直接讀 LightRAG 的儲存檔來斷言（例外：確認答案快取被清時，透過「同一題再問會重新呼叫假 LLM」觀察）。
- 縫（使用者在 grill Q16 確認）：
  - 匯入端：CLI 子行程＋Python API（子行程內呼叫 rag_lab 的模組函式與 `Session`），搭配現有的假 OpenAI server、假 mineru。
  - 下載端：下載腳本的子行程，搭配現有的假 HTTP server、假 Chrome、假 LibreOffice。
  - 不新增其他縫。
- 要涵蓋的行為：
  - 下載端：沒變的檔案修改時間不變；HTML 變了才重新轉檔；轉檔失敗時存檔的 HTML 與文件都不變；PDF 內容變了才換；列表少了一份 → 搬到 `_meta/removed/<日期>/`；列表頁失敗 → 那個類別不搬；有子頁失敗 → 不判斷附件下架；附件只在所有子頁都不連到時才下架；活動過期 → 搬走，圖片只在有空缺時補；仍有效活動的圖片不重新請求；不開更新模式時行為不變（既有測試全綠）。
  - 匯入端：新增、沒變、替換（新版本取代舊版本，查詢只看到新內容）、替換時新版本失敗（寫入一半的內容被刪、舊版本仍在、答案快取不清）、替換中斷後下次補刪舊版本、對照表記的 ID 已不在知識庫、兩個路徑內容相同時刪其中一個不影響另一個、來源已不在只列出、`--prune` 只刪該資料夾的、單一檔案不檢查移除、單一檔案加 `--prune` 結束碼 2、沒有對照表時用檔名對到舊版本（排除已對照到別的路徑的 ID）、檔名對到多份時記成失敗、有改動時答案快取被清而全部沒變時不清、關鍵字快取保留。
- 先例：`tests/test_pipeline.py` 的重複匯入、失敗重試與大表格切表測試；`tests/test_python_api.py` 的 `Session` 測試；`scripts/test_fetch_taishin.py` 的過期判斷與再次執行略過測試。
- 實機驗收（主對話執行，排在截斷調查之後；順序經 grill Q19 修改）：備份 `rag_storage` → 6 個資料夾逐一 `ingest` 建對照表（預期全部沒變）→ 對官網跑更新模式 → 6 個資料夾逐一 `ingest`（不加 `--prune`）→ 「來源已不在」清單給使用者確認 → `--prune` → 抽題 eval 確認答案用到新內容。ASSUMPTION：eval 用 mix 模式；記錄各類別的變動數量、耗時、GPU 記憶體峰值。

## Out of Scope

- 定期或排程自動更新。
- 內容沒變、但處理規則變了的文件（例如 ticket 12 之前匯入、沒有切表的 22 份）：文件 ID 相同，同步視為沒變。這一類由 `.scratch/chunk-truncation/` 的重匯處理。
- 清理 LLM 抽取快取的大小。
- 台新以外的下載來源（論文、多格式文件）的更新模式；匯入端的同步對任何資料夾都適用。
- 改名或搬位置時保留原本的版本：照 GLOSSARY，視為移除一份、新增一份。
- 查詢快取以外的快取失效（例如解析快取）：解析快取鍵本來就含內容雜湊與修改時間。
- 用 `--prune` 刪掉整個已不存在的資料夾的文件（grill Q24）。

- 已查到的事實：
  - 文件 ID 是解析後內容的雜湊，含圖片的絕對路徑；不同路徑、相同內容會得到同一個 ID；
  - LightRAG 1.4.16 的文件狀態只記檔名（目前 311 份檔名都不重複，ID 也都不重複）；
  - LightRAG 的查詢快取鍵含模式、問題、查詢參數與關鍵字，不含檢索到的內容；
  - LightRAG 刪除文件時，預設保留 LLM 抽取快取，並用剩下文件的快取重建受影響的實體與關係；
  - 下載腳本目前再次執行時，已存在的檔案略過、已下載的活動不重新判斷過期；下載清單每次整份重寫，只含這次處理到的文件；網頁類先存原始 HTML 再轉檔；
  - 圖、表、公式描述失敗時，文件記成失敗，但文字 chunk 與實體已經寫進知識庫。
- 下載腳本的更新模式要對真實官網執行，屬於對外請求；實機驗收時照第一次下載的請求間隔。
