# Spec：專案架構文件與 Python 使用範例

## Problem Statement

rag-anything-lab 的 7 張 ticket 都已結案，知識庫（3 篇論文）也建好了，但使用者看不出這個專案的全貌：

- repo 裡每個目錄放什麼、哪些是 git 追蹤的程式、哪些是只存在本機的產物（知識庫、解析結果、量測 log）、哪些能刪，沒有任何文件說明。README 只寫「怎麼建起來、怎麼用 CLI」。
- 每支程式的職責、模組之間誰呼叫誰，只能逐一打開檔案讀 docstring 才知道。
- 知識庫建好之後，除了 CLI 一次問一題之外，不知道怎麼在自己的 Python 程式裡使用它，也沒有範例可以照抄，更不知道範例該放哪個目錄。

試著在同一個 Python 程式裡連續呼叫兩次 `query()` 時，還發現一個 bug：第二次呼叫一定失敗，錯誤訊息是 `Lock is bound to a different event loop`。原因是 LightRAG 的共用鎖是 process 層級的全域物件，第一次初始化時就綁在當時的 event loop 上；而 `rag_lab` 的公開函式每次都用 `asyncio.run` 開新的 loop，收尾時又沒有重置這組鎖。CLI 每次只呼叫一次就結束 process，所以一直沒有發現。`ingest`、`query`、`evaluate` 三個公開函式都會受影響。

## Solution

1. 新增一份架構文件，放在 `docs` 目錄底下，跟現有的 agent 設定文件並列。內容依序是：
   - 整體資料流：PDF → MinerU → LightRAG 建圖 → 知識庫 → 查詢。
   - 每個目錄的用途表：是否進版控、由哪個指令產生、能不能刪。
   - 知識庫內每個檔案的用途。
   - 每個程式檔的職責與主要公開介面，以及模組依賴圖。
   - 「知識庫建好之後怎麼使用」一節，分三種入口：CLI、Python API、範例程式。
2. README 最上方加一行連到架構文件。README 的「使用」一節結尾加「在 Python 裡呼叫」：3 行程式碼，再加一句話指向範例。
3. 在 repo 最上層新增 `examples` 目錄，放一支問答範例：在程式裡寫一份問題清單（2 題），以 mix 模式逐題呼叫 `rag_lab.pipeline.query()`，印出問題和答案。範例在 repo 根目錄用 `python -m examples.<名稱>` 執行。
4. 修正 `rag_lab` 公開函式不能在同一個 process 內重複呼叫的 bug，讓 `ingest`、`query`、`evaluate` 可以在同一個 Python 程式裡任意次數、任意順序地呼叫。

## User Stories

1. 作為使用者，我想用一份文件看懂 repo 裡每個目錄放什麼，以便不用逐一打開目錄猜用途。
2. 作為使用者，我想知道每個目錄是否進版本控管，以便知道換機器時哪些東西要靠 git、哪些要重新產生。
3. 作為使用者，我想知道每個本機產物目錄是由哪個指令產生的，以便需要時能重建。
4. 作為使用者，我想知道每個目錄能不能刪、刪了的代價是什麼（例如知識庫刪了要重新 ingest，3 篇約 1.7 小時），以便清空間時不會誤刪。
5. 作為使用者，我想知道知識庫資料夾裡每個檔案的用途（圖譜、向量庫、文件狀態、LLM 快取、解析快取），以便除錯時知道該看哪個檔，也知道不能手動編輯它們。
6. 作為使用者，我想知道 MinerU 解析輸出目錄為什麼不建議刪（知識庫記錄的是其中圖片的絕對路徑，VLM 增強查詢會讀這些圖片），以便不會在不知情的狀況下讓查詢壞掉。
7. 作為使用者，我想知道開發過程的量測紀錄目錄是什麼、被哪些 ticket 引用，以便判斷要不要保留。
8. 作為使用者，我想看到一張資料流圖，從 PDF 到答案經過哪些步驟、各步驟呼叫哪個模型，以便建立整體概念。
9. 作為使用者，我想知道三個模型（LLM、VLM、embedding）各在哪些步驟被呼叫、由哪個本機 server 提供，以便知道哪個 server 沒開會影響什麼。
10. 作為使用者，我想知道主程式套件裡每個檔案的職責與主要公開函式，以便要改行為時知道該改哪個檔。
11. 作為使用者，我想看到模組依賴圖，以便理解為什麼設定錯誤能在載入重量級套件之前就回報。
12. 作為使用者，我想知道維運腳本各自的用途，以及要用哪個 Python 執行（專案 venv 或 pipx 的 mlx-vlm），以便不會用錯環境。
13. 作為使用者，我想知道測試目錄裡每個檔案測什麼，以及假 server、假 MinerU 的用途，以便知道改了程式要跑哪些測試。
14. 作為使用者，我想知道五種檢索模式（naive、local、global、hybrid、mix）各檢索什麼，以便選擇查詢模式。
15. 作為使用者，我想在架構文件裡看到 CLI 常用指令的總覽，以便不用翻 README 就能開始用。
16. 作為使用者，我想知道 Python API 的三個公開函式（`query`、`ingest`、`evaluate`）的參數、回傳值和失敗時的行為（拋什麼例外、哪些錯誤記在回傳值裡而不拋），以便在自己的程式裡正確處理。
17. 作為使用者，我想有一支可以直接執行的問答範例，以便照抄到自己的程式。
18. 作為使用者，我想知道範例放在哪個目錄、為什麼放在那裡（`scripts` 是維運工具，定位不同），以便自己的程式也知道放哪裡。
19. 作為使用者，我想知道範例為什麼要在 repo 根目錄用 `python -m` 執行（`import rag_lab` 需要 repo 根目錄在 `sys.path` 上；`.env` 的知識庫路徑是相對路徑），以便直接執行檔案出現 `ModuleNotFoundError` 時知道原因。
20. 作為使用者，我想讓範例的設定和 CLI 一樣全部來自 `.env`，以便不用在範例裡另外寫端點和路徑。
21. 作為使用者，我想讓範例出錯時直接帶著 traceback 結束（設定錯、server 沒開、查詢失敗各自是不同的例外），以便看得出是哪一種錯。
22. 作為使用者，我想在同一個 Python 程式裡連續呼叫 `query()` 問很多題，以便批次處理自己的問題清單。
23. 作為使用者，我想在同一個 Python 程式裡先 `ingest()` 新論文再 `query()`，以便用一支程式完成「加文件、提問」。
24. 作為使用者，我想在同一個 Python 程式裡先 `evaluate()` 再 `query()`（或反過來），以便組合不同的公開函式。
25. 作為使用者，我想知道 `query()` 每次呼叫都會重新載入知識庫（每題多幾秒），不適合當常駐服務，以便規劃 web API 或聊天機器人時知道需要另外的介面。
26. 作為使用者，我想從 README 一眼看到架構文件和 Python 用法的入口，以便不會漏掉這些文件。
27. 作為維護者，我想讓範例有自動測試，以便 `rag_lab` 改介面時範例不會在沒人發現的狀況下失效。
28. 作為維護者，我想讓「重複呼叫公開函式」有回歸測試，以便日後升級 LightRAG 或改收尾流程時，這個 bug 不會再出現而沒被發現。
29. 作為維護者，我想讓架構文件的每一條事實陳述都經過沒參與撰寫的人（或 agent）對照實際 repo 檢查，以便文件一開始就是正確的。

## Implementation Decisions

- **架構文件的位置與形式**：一份 Markdown 文件放在 `docs` 目錄底下，進版控。README 只放連結，不重複內容；README 原本的定位（安裝、啟動、操作、實測數據）不變。
- **目錄涵蓋範圍**：git 追蹤的目錄與只在本機的目錄都要寫。本機目錄要標明不進版控、由哪個指令產生、能不能刪；Claude Code 的本機設定目錄只用一句帶過。
- **程式碼說明的深度**：寫到檔案層級，加上每個檔案的主要公開函式和類別、模組依賴圖、資料流圖。不寫到每個函式，因為那會跟 docstring 重複，程式一改就過時。
- **範例的位置**：repo 最上層新增 `examples` 目錄，不放 `__init__.py`，靠 namespace package import。已確認專案 venv 裡沒有已安裝的 `examples` 套件會遮蔽它。不放在 `scripts`，因為 `scripts` 是維運工具（下載、啟動 server、smoke test）。
- **範例的執行方式**：在 repo 根目錄用 `python -m examples.<名稱>`。不在範例裡改 `sys.path`，也不把 `rag_lab` 做成可安裝的套件（不新增打包設定）。
- **範例的內容**：只示範問答。一份 2 題的問題清單，以 mix 模式逐題呼叫 `query()`，每題印出 `Q: <問題>`、`A: <答案>` 兩行。範例不攔例外、不整理回傳結構、不示範模式比較（模式比較已經有 `eval` 指令）。2 題沿用 README 現有的兩個問題。
- **範例只使用現有的公開函式**：不新增 session 之類「初始化一次、問很多題」的 API。每題重新初始化多花的幾秒，相對於一題 52–66 秒的 LLM 生成可以忽略。
- **重複呼叫 bug 的修法**：在 pipeline 的收尾流程最後，呼叫 LightRAG 提供的 `finalize_share_data()` 重置 process 層級的共用鎖。這一步放在收尾的 `finally` 層裡，所以儲存寫回或限流 worker 關閉失敗時也會執行。三個公開函式共用同一個收尾流程，所以三個都一起修好。pipeline 模組 docstring 的關鍵設計決策要補上這一條與原因。
  - 實驗依據：同一支腳本連問兩題，不重置時第二題失敗（rc=1，錯誤為 `Lock ... is bound to a different event loop`）；每題之後重置則兩題都成功（rc=0）。
- **README 的修改**：最上方說明處加一行連到架構文件；「使用」一節結尾加「在 Python 裡呼叫」，內容是 3 行程式碼加一句指向範例與架構文件的話。

## Testing Decisions

- **好的測試**：只觀察外部行為，也就是子行程的結束碼、stdout、產生的檔案，以及假 server 在 HTTP 邊界收到的請求，不斷言內部實作。假 server 的 chat 回應是固定字串，所以只驗證流程能跑完、輸出格式正確，不驗證答案內容。
- **縫 1（既有）**：CLI 子行程 `python -m rag_lab ...`。這次不新增 CLI 測試。
- **縫 2（新增）**：範例子行程 `python -m examples.<名稱>`。先 ingest 一份假 PDF 建出索引，再在 repo 根目錄執行範例。斷言結束碼為 0、輸出恰有 2 行 `Q: `、2 行 `A: `，且答案等於假 server 的固定回應。這個測試同時涵蓋「同一個 process 連續呼叫 `query()` 兩次」。
- **縫 3（新增，使用者選定）**：Python API 子行程。測試以子行程執行一段在同一個 process 裡呼叫 `rag_lab.pipeline` 公開函式的 Python 程式，覆蓋這些順序：
  - `ingest` 後 `query`；
  - `query` 連續兩次；
  - `evaluate` 後 `query`；
  - `ingest` 同一份 PDF 兩次（第二次應略過）。

  斷言結束碼與 stdout 上每一步的結果（答案字串、略過標記、每格答案）。子行程的環境變數組法與 CLI 測試相同（清掉開發機的設定欄位，指向假 server 與暫存資料夾）。這個縫把三個公開函式正式視為公開介面：改簽章或行為時要同步改測試與架構文件。
- **先紅後綠**：縫 2、縫 3 的測試要先在修 bug 之前執行並確認失敗，失敗原因必須是 event loop 錯誤，而不是測試本身寫錯。修好後轉綠。
- **既有測試的參考**：
  - CLI 流程測試的共用基底：啟動假 server、在 PATH 放假 mineru、暫存索引與解析資料夾、組環境變數。縫 2、縫 3 直接沿用。
  - CLI 測試的子行程工具：清掉開發機設定欄位後套用有效基準設定的做法。
  - eval 測試：讀範例題目檔當輸入的做法，縫 3 呼叫 `evaluate` 時可以沿用。
- **架構文件不寫自動測試**：改由一個沒參與撰寫的 agent 做 read-back，逐條核對文件中的事實（路徑是否存在、是否進版控、函式簽章、模組 import、CLI 參數、README 章節號碼），並回報不符的項目。
- **真實 server 驗證**：開著兩個真的 MLX server（記憶體 watchdog 同時運作），在 repo 根目錄實際執行範例一次，記錄結束碼、輸出與耗時。這一步由主對話執行，不平行執行（GPU 記憶體限制）。
- **完整測試**：主測試套件與下載腳本的測試都要全綠，並貼出實際輸出。

## Out of Scope

- 「初始化一次、問很多題」的 session API、常駐服務（web API、聊天機器人）、終端機互動問答。
- 把 `rag_lab` 做成可安裝的套件（新增打包設定）。
- 範例裡的錯誤處理示範、回傳結構整理、檢索模式比較。
- 依函式逐一說明的 API 參考文件。
- 之前記下的其他範圍外問題：
  - 經由 symlink 重複 ingest 時，parse cache 不會命中；
  - `eval` 表格跳脫只處理 `\n`、`\r`；
  - 記憶體 watchdog 腳本沒有執行權限；
  - ticket 04 驗收條件原文仍是舊的 30B 寫法。
